# Talky × Anthropic — *Close the Books*

**Bank reconciliation at scale.** For every bank line of a (fictitious) IBEX-35-sized
industrial group, decide which open items it settles and for how much, explain the
differences, and flag what cannot be identified.

This repo is a **small, working skeleton** with the plumbing already in place:

- it loads the official dumps in seconds,
- it produces a **valid** submission CSV (the official scorer accepts it),
- it **scores itself locally** with the same scorer the leaderboard uses,
- it has one obvious place to implement each hard part.

Baseline right now: `20.5` on the 1-month sample (the official starter scores ~10–15).
A fuller reference implementation that already handles remittance advices and batch
documents (~31 on the same sample) lives in `advanced/`.

The Python environment (devenv, uv, PyTorch, Hugging Face) is documented separately in
[`docs/DEVENV.md`](docs/DEVENV.md).

## 1. Quick start

Three commands, three decisions:

```bash
make data                                  # docs + masters + 1-month sample (~10 MB)
make process PHASE=sample NAME=baseline    # build an artifact into builds/
make evaluate                              # score it (TRAIN/sample) or check coverage
make explain                               # ...and say *why*: lines/pairs lost, per rule
make push PHASE=LIVE                       # upload: asks you to type LIVE / SUBMIT FINAL
make builds                                # the build repository
```

**See the whole pipeline as one page.** `pipeline-map.html` (regenerated by `make map`) is a
technical sheet: one diagram of the pipeline, then one section per stage with the exact rule
and the current numbers. It is generated from the code, so it cannot drift; `make map-serve`
serves it on `localhost:8000` and reloads while you edit a rule.

### Builds are artifacts, not files

Every `process` writes an immutable, self-describing build:

```
builds/20261107-1044-35d1df3b-baseline.csv.gz
       └ date ┘└time┘└ content ┘└ name ┘
                       hash
```

- the hash is of the **CSV content**, not the `.gz` (gzip embeds a timestamp): rebuild the
  same output later and the stamp changes but the hash does not, so "same submission" is a
  provable fact (and `push` uses it to warn about re-sending);
- `builds/<id>.json` is the sidecar (phase, rows, item tables, score, push record) and
  `builds/index.json` is the queryable registry;
- `evaluate` writes the score/coverage back into the registry;
- `push` never guesses which file you meant. It prints the build, the **newest build for the
  phase**, and the **last submission**, and warns when you are pushing something older,
  unevaluated, structurally invalid, or byte-identical to what was already sent.

Upload (needs your team token from the site → Console page):

```bash
read -rs HK_TOKEN && export HK_TOKEN
make push PHASE=LIVE            # = bankrec push LIVE  (latest evaluated build)
make push PHASE=LIVE BUILD=20261107-1044-35d1df3b-baseline
```

**Uploading always asks a human.** `submit.py` prints the phase, the file, the row count and
the sha256 of the *decompressed* CSV, then waits for you to type `LIVE` (or `SUBMIT FINAL`,
because FINAL is a single shot). Anything else aborts, and without a terminal it refuses.
There is no `--yes` and no environment variable that skips it.

**Check the token before you need it.** `make whoami` calls `GET /api/me`, which needs the
team token and nothing else. It uploads nothing, and unlike requesting an upload URL it does
not consume a submission slot:

```bash
read -rs HK_TOKEN && export HK_TOKEN     # or put HK_TOKEN=… in .env (never committed)
make whoami                              # team, status, remaining slots
```

A rejected token is the only cause of `HTTP 401 ... UNAUTHORIZED` from the platform. The
client strips surrounding quotes and a leading `Bearer ` before sending, so a paste that
carries either still works; anything else means the string is not the token the Console page
issued. It is shown once, at registration, and there is no self-service reset: ask the
organisers to reissue it. `pipeline-map.html` and `make map` are unrelated to it.

## 2. The task in one paragraph

The group has 12 currencies, 13 banks and ~50 accounts. A bank line can clear **one
invoice, 300 invoices**, or nothing at all (fees, payroll, cash-pool sweeps, tax…).
The hard part is not arithmetic, it is *evidence*: invoice numbers arrive truncated,
without prefix or with typos; a parent company pays for its subsidiaries; one SEPA
batch is a single bank line for 400 receipts; the reason for a deduction only exists
in a remittance advice PDF that may arrive days later.

You must explain **every** bank line. Lines you omit count as wrong.

## 3. Scoring (this is what to optimise)

```
score = 100 × (0.50 × allocation F1        # (bank line, item) pairs, amount within tol.
             + 0.30 × transaction accuracy # whole set of (item, amount, exception) per line
             + 0.20 × exception macro-F1)  # mean F1 over non-empty exception classes
```

- **Allocation F1** rewards *recall*: a 1:N payment where you emit 1 of 25 items scores
  terribly. Precision is easy (be conservative), recall is where the points are.
- **Transaction accuracy** requires the exact set — one missing item loses the line.
- **Exception macro-F1** is an *average over classes*, so `SHORT_WITHHOLDING` (8 cases)
  is worth as much as `PARTIAL` (466). Do not ignore the rare codes.
- Amount tolerance: `|submitted − golden| ≤ max(0.01, 0.5 % of golden)`.

Local scoring is the real thing — `evaluate.py` runs `vendor/bankrec_score.py`, the
file the server uses. Trust it, not your intuition.

**A number is not an explanation.** `make explain` (or `evaluate --explain`) diffs the
build against the golden and says *why* the score is what it is: which failure kind
lost the most lines (missing item, extra item, amount off, wrong exception, a real
settlement filed as a bank fee…), how many allocation pairs that cost, which exception
classes were never emitted, and example bank lines for each. It is derived from the same
golden the scorer uses, so it can never disagree with the number.

For a per-rule view (`process --trace` + `explain`), each build carries a
`<build-id>.trace.jsonl.gz` sidecar saying which rule fired on every line and how many
candidates it had to choose from. That is how "exact_ref looks precise" becomes
"exact_ref is wrong on 44 % of the lines it claims" — the report tells you where to
work next. Trace recording is a hook (`hooks.py`); it observes decisions and cannot
change the submission, because matching is a chronological book (see CLAUDE.md §7).

### Experiments and versions (no tracking server)

MLflow answers "which run produced this number?" when runs are cheap and distributed.
Here the artifact is already content-addressed (`builds/<stamp>-<sha8>-<name>`), the score
comes from a vendored scorer over a fixed golden, and the registry is one JSON file, so a
tracking server would add a database and a UI without adding a fact.

What was missing is **provenance** and a **diff**. Every build now records the git commit
and dirty flag, a hash of `src/` + config (so uncommitted experiments are still
reproducible), and a cheap data-snapshot fingerprint. That gives three independent
versions of one run:

| version | what it is | where |
|---|---|---|
| code | git commit + `code_sha` of the exact files | build sidecar |
| artifact | sha256 of the decompressed CSV | build id + sidecar |
| data | `manifest.json` hash + phase file sizes | build sidecar |

Three commands make it useful:

```bash
make runs                       # experiment list: score, Δ vs baseline, code, note
make compare BEFORE=<id> AFTER=<id>   # fixed/broken lines, per-segment and per-kind deltas
make report BUILD=<id> MD=1     # markdown: provenance + score + `--explain`
make documents                  # preprocessing: parsed documents, integrity, attachment
```

Preprocessing has its own report for the same reason matching does: a silent drop is
invisible in the score. `make documents` shows, per phase, files → groups → entries per
document family, whether entries carry a usable reference and amount, whether they sum
to the batch/deposit total the bank moved, parse coverage per advice format (CSV/TXT
parsed vs XLSX/PDF with no extractor), and how many bank lines the index can explain.
The compact summary is stored on every build (`build.documents`), so `report` includes it
and `compare` shows when a parser change moved entries or integrity warnings.

Preprocessing stages that produce a *report* but no submission (PDF layout/language,
advice extraction, payment-run normalisation) register in `stages/` with the same
provenance (git commit, code sha, data fingerprint) and the sha256 of every file they
wrote:

```bash
python -m bankrec stage --stage pdf_layout --phase sample \
  --note "fusion + quality gate" --metric accuracy=0.93 --metric docs=1200 \
  --report experiments/pdf_layout/out/lang_bench.json
make stages [STAGE=pdf_layout] [PHASE=sample]
```

A stage run's id is content-addressed (`stage-phase-<sha8>` over metrics + report
hashes + code sha), so re-running the same experiment is idempotent and a code change
that leaves the metrics identical still gets a new id.

`process --note "hypothesis" --tag v2` writes the hypothesis next to the run, so
`make runs` is the lab notebook. `compare` uses the strict scorer definition of a
correct line (exact item set, amounts within tolerance, same exceptions); a tie-break
that swaps one wrong item for another is not counted as progress. Regressions are
printed with the bank text, so a +583 net that broke 13 lines is visible, not hidden by
the average.

```

├── archives/                ← exactly what the server served (sha256 in the manifest)
├── manifest.json            ← url, bytes, sha256, extraction log
├── masters/                 ← shared master data (snapshot 2025-12-31)
├── sample/                  ← one labelled month (from the docs archive)
├── train/      train-lite/  ← four labelled years (lite: raw files only from 2024-07)
├── live/       final/       ← the scored phases (final ships masters_final/)
```

```bash
make data        # docs + masters + sample
make data-lite   # + train-lite (460 MB)
make data-all    # + train, live, final when published (~1.2 GB)
make list        # what is here, what is missing
make verify      # re-hash the archives against the manifest
```

Archives are kept by default: they are the provenance of every score you report and
`--verify` can prove your data still matches what the organisers published. Use
`--no-keep-archives` if disk is tight.

Each phase directory has the same layout:

```
<phase>/    bank_transactions.csv.gz      ← the lines you must explain
            ar_invoices.csv.gz  ap_invoices.csv.gz  credit_notes.csv.gz
            open_items_at_start.csv.gz    (LIVE/FINAL only)
            golden_allocations.csv.gz     (TRAIN/sample only)
            bank_statements/              raw N43 / MT940 / camt.053 files
            direct_debit_batches/ card_settlements/ cheque_deposits/ payment_runs/
            remittance_advices/ pdfs/     ← 1:N and "why it differs" evidence
```

Columns you will use constantly:

| table | columns |
|---|---|
| `bank_transactions` | `bank_txn_id`, `account_id`, `entity`, `booking_date`, `amount` (signed, account currency), `currency`, `text`, `ref1`, `ref2`, `counterparty_name`, `counterparty_account`, `end_to_end_id`, `remittance_info`, `orig_amount`, `orig_currency` |
| AR/AP invoices | `item_id`, `document_number` (what the customer quotes), `issue_date`, `due_date`, `currency`, `net/tax/total_amount`, `payment_terms`, `customer_po` |
| credit notes | `item_id`, `side` (AR/AP), `document_number`, `total_amount`, `related_document`, `reason` |
| `open_items_at_start` | `item_id`, `item_type`, `party_id`, `document_number`, `currency`, `total_amount`, `open_amount` |
| `golden_allocations` | `bank_txn_id`, `item_id`, `amount`, `category`, `exception`, `segment`, `difficulty` |

**`segment` is your roadmap.** It tells you which pattern produced each row
(`ar_1toN_remittance`, `ap_partial`, `nonitem_bank_fees`, …). Sort segments by
`rows × (1 − your_coverage)` and work top-down.

## 6. The submission contract (full detail in `docs/FORMAT.md`)

One CSV, UTF-8, comma, header, optionally `.csv.gz`, **one row per allocation**:

```csv
bank_txn_id,item_id,amount,category,exception
BT-2025-0001234,ARI-2025-0456789,1210.00,,
BT-2025-0001234,ARI-2025-0456790,605.00,,
BT-2025-0001240,,,BANK_FEES,
BT-2025-0001300,ARI-2025-0400001,980.00,,SHORT_DISCOUNT
BT-2025-0001301,,,UNIDENTIFIED,UNIDENTIFIED
BT-2025-0001302,ARI-2025-0400002,400.00,,PARTIAL
```

| column | rule |
|---|---|
| `bank_txn_id` | a bank line of the phase you submit; omitted lines count as wrong |
| `item_id` | `ARI-`/`ARC-`/`API-`/`APC-` + year + 7 digits; empty when the line settles no item |
| `amount` | amount of the item cleared by this line, **in the item currency, positive**, dot decimals; empty when `item_id` is empty |
| `category` | only for no-item lines, from `masters/categories.csv` |
| `exception` | empty or one of the closed list below |

Limits: ≤ 60 MB uncompressed, ≤ 3,000,000 rows, max one no-item row per line, no
duplicate `(bank_txn_id, item_id)`, and a line cannot mix item rows and a category row.
`make validate` checks all of this before you upload.

## 7. Policy cheat sheet (`docs/POLICIES.md` has the exact wording)

**Exceptions**

| code | when | amount |
|---|---|---|
| *(empty)* | paid as documented, last instalment, credit notes netted | open amount |
| `PARTIAL` | item still open afterwards, no specific reason | cash applied |
| `SHORT_DISPUTE` | customer deducted with a stated reason (advice) | cash applied |
| `SHORT_DISCOUNT` | within terms + 3 days grace, cash = total − discount % | full open amount |
| `SHORT_BANK_CHARGES` | intermediary fee: shortfall ≤ 60 EUR **and** ≤ 2 % | full open amount |
| `SHORT_WITHHOLDING` | tax withheld: 1.25 / 1.5 / 10 % | full open amount |
| `OVERPAYMENT` | paid more than one invoice's open amount | full open amount |
| `FX_DIFFERENCE` | line currency ≠ item currency (replaces discount/charges/withholding) | full open amount |
| `DUPLICATE_PAYMENT` | item already settled, paid again | cash paid again |
| `RETURNED` | SEPA/cheque/card return re-opens the item | amount reversed |
| `UNIDENTIFIED` | receipt with no matching open item | — (with category `UNIDENTIFIED`) |

**Categories** (no-item lines): `BANK_FEES`, `INTEREST_INCOME`, `INTEREST_EXPENSE`,
`PAYROLL`, `SOCIAL_SECURITY`, `TAX_PAYMENT`, `TAX_REFUND`, `LOAN_DRAWDOWN`,
`LOAN_REPAYMENT`, `LEASING`, `FX_DEAL`, `CASH_POOL`, `INTERCOMPANY`,
`INTERNAL_TRANSFER`, `CUSTOMER_ADVANCE`, `CUSTOMER_REFUND`, `SUPPLIER_REFUND`,
`CARD_EXPENSES`, `INSURANCE`, `BANK_REVERSAL`, `UNIDENTIFIED`.

**Matching policy highlights**

1. Who paid ≠ who was invoiced: a parent pays for its subsidiaries; confirming banks and
   collection agencies pay on behalf of a customer.
2. Batches: one line = all receipts of the `direct_debit_batches/` file, all orders of a
   `card_settlements/` file, all cheques of a deposit, all documents of a `payment_runs/` file.
3. Remittance advices name the documents, the deductions and the reasons — the only
   source for 1:N and `SHORT_DISPUTE`. They may arrive after the cash.
4. Same amount, several open invoices → **oldest first (FIFO)**; a month in the text
   means that service month.
5. "Anula y sustituye": a payment citing a cancelled invoice settles its replacement.
6. Returns are often re-presented later (`re_presentation=Y`) or paid by transfer.
7. Deliberate drift: Moncayo migrates N43 → camt.053 on 2025-10-01, a key account changes
   its advice layout in 2025-09, and a ZAR subsidiary appears in FINAL.

## 8. Where to implement what

### Two engines: `--engine alt` (default) and `--engine baseline`

`process` picks the matcher:

```bash
make process PHASE=sample                      # alt   (operation-first)
$(PY) -m bankrec process --phase sample --engine baseline
```

| engine | sample score | alloc F1 | txn acc | exception macro-F1 |
|---|---|---|---|---|
| `baseline` (`matching.py` + `rules.py`) | 39.56 | 0.490 | 0.469 | 0.048 |
| `alt` (`alt/engine.py`) | **73.60** | 0.830 | 0.734 | 0.504 |

They answer the same question in opposite orders. The baseline asks *which items could
this line settle* and then checks whether a subset adds up. `alt` asks **what kind of
banking operation is this line** first, because for four of the hardest segments the item
list is not something to infer at all — it is written down in `direct_debit_batches/`,
`card_settlements/`, `cheque_deposits/`, `payment_runs/` or a remittance advice, and the
only real question is which file row belongs to which bank line. Its resolvers run in
order of how much the evidence can be trusted (batch/run id → advice reference → amount
fallback → references in the text → payer and amount), and the inference resolvers are
arbitrated by *which proposal actually adds up to the cash* rather than by their order.

The baseline is kept, runnable and unchanged: it is the control for every measurement,
and `--engine baseline` still reproduces 39.56 exactly.

### `matching.py` — what does this bank line settle?

The baseline does three things: exact document reference in the text, party (IBAN or
fuzzy name) + exact amount, and a unique amount fallback. The TODOs mark the next
branches, roughly in order of value:

| branch | segment(s) | idea |
|---|---|---|
| 1:N references | `ar_1toN_text`, `ar_n_to_m` | sum the referenced items; accept when the total matches |
| remittance advice | `ar_1toN_remittance`, `ar_short_dispute` | parse the advice (csv/txt/pdf), use its rows and reasons |
| aggregate documents | `ar_dd_batch`, `ar_card_settlement`, `ap_confirming` | expand the batch/run file, then match each entry |
| credit notes | `*_credit_note_netted` | a payment can net an ARC/APC: add it as a positive row |
| FIFO / service month | `ar_same_amount_fifo`, `ar_same_amount_month` | break amount ties by issue date / text month |
| duplicates & returns | `*_duplicate*`, `*_returned*` | keep settled items indexed too; `RETURNED` re-opens |

### `rules.py` — what code goes on the row?

`exception_for()` is called once per emitted item row; `category_for()` once per line
that settles nothing. Both start from the folded bank text. Add the discount /
withholding / bank-charge arithmetic from the cheat sheet — each one is worth real points
in TRAIN, and the macro-F1 weight makes the rare classes matter.

### Workflow that actually works

```bash
# 1. look at the biggest gap
python - <<'PY'
import polars as pl
g = pl.read_csv("data/sample/golden_allocations.csv.gz", infer_schema_length=0)
print(g.group_by("segment").agg(pl.len().alias("rows"), pl.col("bank_txn_id").n_unique().alias("lines")).sort("rows", descending=True))
PY

# 2. read 20 examples of that segment (join to bank_transactions, look at `text`)
# 3. implement ONE branch, then build and evaluate it
make process PHASE=sample NAME=tweak && make evaluate
# 4. keep it only if the score went up (compare per-segment accuracy too)
```

Use `notebooks/` for exploration. Keep `src/` clean: the pipeline should be runnable
at any commit.

## 9. Performance notes

Measured on this machine with the official data:

| phase | bank lines | items loaded | index build | matching | total |
|---|---|---|---|---|---|
| `sample` | 8,499 | 65,846 | 1.9 s | 3 s | **~5 s** |
| `live` | 203,083 | 1,031,576 | 8 s | 80 s | **~89 s** (≈2,300 lines/s) |
| `live` + `train` items | 203,083 | 6,350,310 | 48 s | 767 s | ~815 s — *wrong, see below* |

- **Do not load `train` for LIVE/FINAL.** `open_items_at_start.csv.gz` already carries
  every balance from the previous phases; adding TRAIN on top marks four years of settled
  invoices as open. `Phase.items()` now ignores the extra tables and says so.
- **Tolerance windows scale with the amount.** `max(0.01, 0.5 %)` on a 1 M € line is a
  5,000 € window; hundreds of items live there and none is a better guess than another,
  so `items_by_amount` returns nothing above 250 candidates instead of ranking noise.
- **Amount before name.** The amount window is selective and cheap; name tokens are not
  (`POOL` alone matches thousands of parties). `_amount_and_name` checks names only for
  items whose amount matches, and the fallback uses *selective-token blocking*: start
  from the rarest token's candidate set and intersect, instead of expanding every token.
  This took LIVE from 1.9 ms to 0.45 ms per line.
- **Everything derived from `masters/` is built once** (`iban_owner`, `party_names`,
  `party_tokens`). A `@property` that re-scans 60 k customers per line is how a 5-second
  run becomes 30 minutes.
- **Runs are atomic and exclusive.** Output is written to `.<name>.<pid>.tmp` and renamed;
  a lock file stops two runs from writing the same submission (a killed or concurrent run
  used to leave trailing zeros in the `.gz`, which the scorer rejects).
- Use `--limit N` for development iterations and watch the `eta` lines on long runs.

## 10. Checklist before you submit

- [ ] `make evaluate` on the build you are about to push, or `make validate BUILD=…`
- [ ] `make builds` — confirm you are pushing the newest build for the phase
- [ ] `make score` on `sample`/`train` improved (compare per-segment accuracy, not just total)
- [ ] no data leakage: you only used `golden` from TRAIN, never tried to obtain LIVE/FINAL labels
- [ ] `.csv.gz`, ≤ 60 MB uncompressed, ≤ 3 M rows
- [ ] `make push PHASE=LIVE` — you saw the row count and sha256, and **you** typed `LIVE`
- [ ] FINAL: one shot — the first **valid** file counts, so validate on LIVE first
