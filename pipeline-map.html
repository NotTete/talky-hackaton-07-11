Load and canonicalise

src/bankrec/data.py Phase · Masters · FX · to_cents
invariant
Money is an integer from to_cents onwards. That function is the only place a float exists, and the tolerance below it is max(0.01, 0.5%) in integer cents.
note
Bank lines are sorted by (booking_date, bank_txn_id) once, at load. PARTIAL, RETURNED and DUPLICATE_PAYMENT are properties of a moment, so order is part of the data model, not a convenience.
note
Every master-derived lookup is built in Masters.__init__: 18 category keywords, terms, IBAN owners, own accounts, party names. Nothing O(masters) runs inside the per-line loop.

Index the open items

src/bankrec/alt/ledger.py Ledger
note
One pass over 65,846 items converts the polars frame into dicts and builds every key list. After that the per-line loop never touches a DataFrame: the candidate set is a handful of dict lookups.
invariant
open and paid are the only mutable state. apply() consumes an item, reopen() gives it back on a return. The key lists never change, so lookups stay logarithmic.
failure mode
Anything that batches lines out of order loses the exceptions that depend on sequence: a returned direct debit re-opens an item, and a second payment can only be duplicate because the first one closed the item.

Resolve the line

src/bankrec/alt/engine.py Engine.resolve
note
The engine asks what kind of operation the line is before it looks for items. Document resolvers read a file that already lists the answer (a batch, a card settlement, an advice); the first one that fires wins outright.
note
Inference resolvers each propose a set of items, and the winner is the one whose amounts net to the cash. A truncated reference that resolves to one invoice must not beat a sweep that sums to the statement.
note
PDF facts enter as evidence only: a replacement clause, a credit-note direction, an instalment plan, a retention. Recall is 0.788 against precision 0.888: the missing points are on the proposal side.

Allocate the cash

src/bankrec/alt/engine.py Engine._rows_from_docs · _share · _commit
invariant
Resolvers only propose rows. _accept is the single place that moves the book, so a later line sees the balance this one left behind and PARTIAL, DUPLICATE_PAYMENT and RETURNED stay possible.
note
Credit notes net against invoices: the cash to distribute is the cash plus the notes, and each note is a full positive row with no exception. Several named invoices with no amounts are cleared in full before any residual is sliced.
note
Amounts are compared in EUR and submitted in the item currency; _in_currency and _to_item are the only conversion points.
alt/engine.pyshortened
# resolve(): document steps, then inference steps judged by the cash
for name in self.INFERENCE_STEPS:
    rows = steps[name](ctx)
    gap = abs(_net(rows, self.ledger) - abs(ctx.cash))
    if gap <= tol:
        return self._accept(name, rows)   # _commit moves the book

# credit notes net: invoices - notes == cash, notes are full positive rows
def _commit(self, rows):
    for row in rows:
        if row.exception == "RETURNED": self.ledger.reopen(...)
        else: self.ledger.apply(row.item_id, row.cents)

Name the difference

src/bankrec/alt/excepts.py Exceptions.decide · Categories.of
note
Two closed lists, one per row shape: an item row carries an exception, a no-item row carries a category. The server rejects the whole file for an unknown value, so both lists are constants and both are validated before upload.
note
Default is the empty code: a wrong code costs the whole transaction, a blank one only costs the code. Exceptions.decide names the shortfall between the open balance and the cash.
note
Categories are the fallback for lines that settle nothing: 1,650 of 1,730 no-item rows end in the sign default, the rest come from the IBAN, bank-code and keyword tables.

Process, validate, evaluate

src/bankrec/pipeline.py process · evaluate.score_file · hooks · insights
invariant
Every bank line appears exactly once, as item rows or as a single category row, and never as both. No duplicate (bank_txn_id, item_id). make validate checks the same rules the server does, before any upload.
note
The file is scored offline with the vendored scorer, so this number is the leaderboard's number, and the 65 segments below are the same slices it reports.
note
The exception weight is worth 10.14 points because only 9 of 10 codes is ever emitted. Macro F1 averages over classes, not rows, so one rare code is worth as much as a segment with hundreds of lines.
note
process --trace runs a DecisionHook after the matcher has already decided (it observes, it cannot settle an item — that would break the chronological book in the index stage) and writes which rule fired and how many candidates it had per line. evaluate --explain reads that sidecar and the golden file to turn the score into a report: which failure kind lost the most lines, and which rule to fix next.

invariant
No flag, no environment variable and no --yes skips the gate. Without a terminal it refuses before any HTTP call, so an agent or CI can build and validate but cannot spend the submission.
note
The printed sha256 is of the decompressed CSV, because gzip embeds a timestamp: two identical files have different .gz hashes, so only the decompressed hash identifies what is being uploaded.
note
FINAL is one scored submission per team, so its phrase is longer (SUBMIT FINAL) and the row count, size and limits are checked before the prompt, not after.
